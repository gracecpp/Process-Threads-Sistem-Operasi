Lesson 6 Concept + tiny C

Race conditions

Why counter++, run by two threads, does not add up.

Recall

The bonus at the end of Lesson 5: two threads each did counter++ a million times. You expected 2 000 000. You got some number smaller — and different every run.

That's a race condition. Let's see exactly what happened.

The one idea

counter++ looks like one step in C. To the CPU, it is three:

  1. Read counter from memory into a register.
  2. Add 1 to the register.
  3. Write the register back to memory.

The kernel can pause a thread between any two instructions. So threads A and B can interleave in the middle of a single counter++.

The losing interleaving 
counter = 100.

Thread A: read counter -> reg = 100
                                     Thread B: read counter -> reg = 100
                                     Thread B: reg = 101
                                     Thread B: write reg -> counter = 101
Thread A: reg = 101
Thread A: write reg -> counter = 101

counter is 101. Two increments happened. Only one counted.

This is called a lost update. Every time the kernel picks that interleaving, one increment vanishes. Do it a few thousand times and your total is short by thousands.

The definition

A race condition is a bug where the correctness of your program depends on the timing / ordering of threads, and the kernel gives you no such guarantee. The section of code involved — the read-modify-write on counter — is called a critical section.

See it (and measure it)

#include <stdio.h>
#include <pthread.h>

int counter = 0;

void *bump(void *arg) {
    for (int i = 0; i < 1000000; i++)
        counter++;                  /* THE CRITICAL SECTION */
    return NULL;
}

int main(void) {
    pthread_t t1, t2;
    pthread_create(&t1, NULL, bump, NULL);
    pthread_create(&t2, NULL, bump, NULL);
    pthread_join(t1, NULL);
    pthread_join(t2, NULL);
    printf("counter = %d  (expected 2000000)\n", counter);
    return 0;
}

$ ./race
counter = 1348217  (expected 2000000)
$ ./race
counter = 1502994  (expected 2000000)
$ ./race
counter = 1197033  (expected 2000000)

Three runs, three wrong answers, all different. That variability is the signature of a race.

The scary part

On a fast enough machine with light contention, races sometimes look like they "work" for months, then blow up in production. A race that's silent 99.99% of the time is still a bug — the ordering the kernel gave you today isn't a guarantee for tomorrow.

What DOESN'T fix it

  • Making the variable volatile — volatile tells the compiler not to optimize accesses away. It doesn't make read-modify-write atomic. Doesn't help.
  • Just adding printfs — they change timing, so the bug hides. Doesn't fix it. This is called a Heisenbug.
  • Running on one CPU core — even a single core context-switches between threads. The race still fires.

What DOES fix it

You need to make the three sub-instructions of counter++ behave as one indivisible step. Either:

  1. Wrap them in a mutex — a lock that lets only one thread into the critical section at a time. This is Lesson 7.
  2. Use an atomic instruction — special CPU operations designed for exactly this. (<stdatomic.h> in C11; a topic for later.)

Check yourself

The counter++ in C compiles to how many CPU steps?

Read into register, increment the register, write back. Any two of those can be interleaved with another thread — that's the crack the race slips through.

A race gives the wrong answer 1 run in 1000. It's:

Timing changes with load, hardware, and updates. A rare race becomes a common one at the worst moment. Fix it once you can reproduce it — even barely.

Which of these actually fixes the counter race?

Only real mutual exclusion makes the read-modify-write indivisible. volatile is about compiler optimization, not atomicity. printfs just change the timing.

Try it yourself

  1. Run the race demo above 10 times. Record the results. Note how far short of 2 000 000 they are, and how they vary.
  2. Try to make it "worse": pin your machine's CPU load, or increase the loop to 10 million. The lost fraction usually grows.
  3. Come back after Lesson 7 and re-run with a mutex. Confirm you get exactly 2 000 000, every time.
