Lesson 2 syscall + tiny C

fork(): the call that returns twice

One line of C. Two processes come out the other side.

Recall from Lesson 1

A process is a running program with its own private memory and its own PID. So far we've only made processes the "obvious" way: by typing ./hello_pid at the shell.

Question: how does the shell itself make a new process when you press Enter? The answer is one Unix system call: fork().

The one idea

fork() asks the kernel: "please clone me." The kernel makes a near-perfect copy of the current process — same code, same memory contents, same open files — and now two processes are running the exact same program, sitting on the exact same line of code.

The trick is: how does each copy know whether it is the original ("parent") or the clone ("child")? The kernel tells them by giving each a different return value from that single fork() call:

The rule

In the parent, fork() returns the child's PID (a positive number).
In the child, fork() returns 0.
On failure (in the parent only), fork() returns -1.

So the same line of code runs in two processes, and each one gets a different answer. That is why we say fork returns twice.

See it in C

#include <stdio.h>
#include <unistd.h>    /* fork(), getpid(), getppid() */

int main(void) {
    printf("Before fork: I am %d.\n", getpid());

    pid_t rc = fork();

    if (rc < 0) {
        perror("fork failed");
        return 1;
    } else if (rc == 0) {
        /* child branch: fork() returned 0 here */
        printf("  child : pid=%d, parent=%d\n", getpid(), getppid());
    } else {
        /* parent branch: fork() returned the child's pid here */
        printf("  parent: pid=%d, child=%d\n", getpid(), rc);
    }
    return 0;
}

Typical run:

$ cc fork_demo.c -o fork_demo
$ ./fork_demo
Before fork: I am 51001.
  parent: pid=51001, child=51002
  child : pid=51002, parent=51001

Notice: "Before fork" printed once — there was only one process then. After fork(), both branches of the if ran, because both branches ran, in different processes. Same code file, two live workers.

Gotcha

The order of the two lines after fork() is not guaranteed. The child might print first, or the parent might. The kernel schedules them independently. Never assume an order — that is your first taste of concurrency.

What gets copied?

Almost everything the process has, at the moment of the call:

  • All of memory — variables, heap, stack. But the copies are independent. If the child changes a variable, the parent doesn't see it.
  • Open file descriptors (stdin/stdout/stderr, open files, sockets). Parent and child share these — writing to stdout from either goes to the same terminal.
  • The current instruction. Both continue on the very next line after fork().

Two things the child gets fresh: a new PID, and a parent PID pointing at the original.

Check yourself

In the child process, what value does fork() return?

Zero in the child; the child's PID in the parent; -1 on failure. That's the whole convention — it's how each side tells which one it is.

After fork(), the child modifies a global variable x. What does the parent see when it reads x?

Each process gets its own copy of memory. Writes in one are invisible to the other. This is process isolation — the safety net that keeps unrelated programs from stepping on each other.

You call fork() twice in a row, no other logic. How many processes exist afterward?

First fork: 1 → 2. Both survivors run the second fork: 2 → 4. Each fork doubles the process count. This is a classic exam trick.

Try it yourself

  1. Save the program as fork_demo.c, compile, and run it a few times. Note the PIDs change each run.
  2. Add a line before fork(): int x = 100;. In the child branch, do x = 999; then print x. In the parent branch, print x. Confirm the parent still sees 100.
  3. Bonus: put a second fork() right after the first, print getpid(), and count how many lines print. Convince yourself it's four.
