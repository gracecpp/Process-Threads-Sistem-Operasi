Lesson 8 capstone

Build a tiny shell

Every syscall from L2–L4, wired together into a program you can actually type into.

Why this lesson

So far each syscall lived in its own toy program. A shell is where they finally meet. Bash, zsh, sh, dash — every one of them is fundamentally the loop you're about to write. The rest is decoration: history, tab-completion, prompts, colors. The heart is about 40 lines of C.

When you finish this lesson, you will have typed ls -l into a program you wrote, and watched it run. That's the "aha" the whole mission was aiming at.

The recipe (recall)

From Lesson 4, the core loop of every shell:

while (read a line from the user) {
    split the line into words;
    fork();
    if (child) execvp(words[0], words);
    else       waitpid(child_pid, ...);
}

That's it. Four verbs: read, fork, exec, wait.

Stage 1 — the skeleton

Start here. It prompts, reads a line, and echoes it back. No forking yet.

#include <stdio.h>
#include <stdlib.h>
#include <string.h>

int main(void) {
    char line[1024];
    for (;;) {
        printf("tsh> ");
        fflush(stdout);
        if (!fgets(line, sizeof line, stdin)) break;   /* Ctrl-D exits */
        line[strcspn(line, "\n")] = 0;                  /* strip newline */
        if (line[0] == 0) continue;                     /* empty line */
        printf("you said: %s\n", line);
    }
    return 0;
}

Save as tsh.c, then:

$ cc -Wall -o tsh tsh.c
$ ./tsh
tsh> hello
you said: hello
tsh> ^D
$
Checkpoint

You have a REPL. Ctrl-D exits cleanly because fgets returns NULL on EOF. Nothing runs yet — but the skeleton is real.

Stage 2 — split the line into words

execvp wants an array like {"ls", "-l", "/", NULL}. The classic tool is strtok, which walks a string and hands back one whitespace-separated token per call. 

#define MAX_ARGS 64

static int split(char *line, char *argv[]) {
    int n = 0;
    char *tok = strtok(line, " \t");
    while (tok && n < MAX_ARGS - 1) {
        argv[n++] = tok;
        tok = strtok(NULL, " \t");
    }
    argv[n] = NULL;    /* execvp requires NULL-terminated array */
    return n;
}

Drop that above main, and inside the loop replace the "you said" line with:

char *argv[MAX_ARGS];
int argc = split(line, argv);
if (argc == 0) continue;
for (int i = 0; i < argc; i++) printf("[%d] %s\n", i, argv[i]);

tsh> ls -l /tmp
[0] ls
[1] -l
[2] /tmp

Stage 3 — fork & exec

Now the payoff. Replace the print loop with the real thing:

#include <unistd.h>
#include <sys/wait.h>

pid_t pid = fork();
if (pid < 0) { perror("fork"); continue; }

if (pid == 0) {
    /* child: become the requested program */
    execvp(argv[0], argv);
    perror(argv[0]);        /* only reached if exec failed */
    _exit(127);              /* traditional "command not found" code */
} else {
    /* parent: wait for the child to finish */
    int status;
    waitpid(pid, &status, 0);
}

Rebuild and try it:

tsh> ls
tsh  tsh.c
tsh> echo hello world
hello world
tsh> date
Mon Sep 21 12:00:00 UTC 2026
tsh> nope
nope: No such file or directory
tsh> ^D

You just wrote a shell. Every command you typed followed the full fork→exec→wait dance from Lessons 2–4.

Stage 4 — one built-in: cd

Try cd /tmp. It "works" — no error — but pwd shows you didn't move. Why?

Think it through

If cd ran in the child (after fork), the child's directory would change… then the child would exit. The parent shell — the one that survives to prompt again — never moved. cd must run in the shell process itself. That's why every shell has "built-in" commands: they're the ones that can't be a separate program.

Fix: before the fork, check for built-ins:

if (strcmp(argv[0], "cd") == 0) {
    const char *dir = argv[1] ? argv[1] : getenv("HOME");
    if (chdir(dir) != 0) perror("cd");
    continue;                /* skip the fork/exec path */
}
if (strcmp(argv[0], "exit") == 0) break;

Now cd and exit behave. Congratulations — you have discovered, from first principles, why cd is always a shell built-in and never a program in /usr/bin.

Check yourself

Why can't cd be an ordinary program in /bin?

A forked child that calls chdir changes only its own working directory, then exits. The parent shell is untouched. So cd must run in the shell process itself — a built-in.

What is the NULL at the end of argv for?

execvp has no separate argument count; it walks the array until it hits NULL. Forget it and exec reads past your data — undefined behavior.

What if you removed the waitpid in the parent branch?

Without waitpid, the shell prints its next prompt immediately while the child is still running. Output interleaves; finished children become zombies (see L3). This is, in fact, exactly how the shell's & (background) works.

Stretch goals

Pick one — each is a small extension of what you have:

  1. Background jobs: if the last token is &, drop it and skip the waitpid. You've just implemented ls &.
  2. Redirection: if argv contains >, remove it and the following filename, then in the child call freopen(filename, "w", stdout) before execvp. You've implemented ls > out.txt.
  3. Exit status: after waitpid, print WEXITSTATUS(status) when it's nonzero. That's what $? is in bash.
  4. A prompt with the cwd: use getcwd to show where you are.

Each of these is 3–5 lines. None require anything you haven't seen.
