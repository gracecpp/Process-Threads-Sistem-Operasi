Mutex: the fix

One key. One person in the room at a time.

Recall

Lesson 6 showed counter++ losing updates because two threads interleave in the middle of the three-step read-modify-write. We need to make that section indivisible.

The one idea

A mutex (mutual exclusion lock) is a small object with two states: locked or unlocked. It supports two operations:

  • lock: if the mutex is unlocked, take it and continue. If it's already locked, block until the current holder releases it.
  • unlock: release the mutex so another waiting thread can take it.

By wrapping a critical section in lock / unlock, you guarantee only one thread runs that code at a time. The other threads wait in line.

Mental model

Imagine a single-occupancy bathroom with one physical key. You take the key (lock), do your business (critical section), hang the key back (unlock). Anyone else waits at the door.

See it in C

#include <stdio.h>
#include <pthread.h>

int counter = 0;
pthread_mutex_t lock = PTHREAD_MUTEX_INITIALIZER;

void *bump(void *arg) {
    for (int i = 0; i < 1000000; i++) {
        pthread_mutex_lock(&lock);
        counter++;                     /* only one thread here at a time */
        pthread_mutex_unlock(&lock);
    }
    return NULL;
}

int main(void) {
    pthread_t t1, t2;
    pthread_create(&t1, NULL, bump, NULL);
    pthread_create(&t2, NULL, bump, NULL);
    pthread_join(t1, NULL);
    pthread_join(t2, NULL);
    printf("counter = %d\n", counter);
    return 0;
}

$ cc -pthread mutex_demo.c -o mutex_demo
$ ./mutex_demo
counter = 2000000
$ ./mutex_demo
counter = 2000000
$ ./mutex_demo
counter = 2000000

Every run: exactly 2 000 000. The race is gone.

Three rules for using a mutex

  1. Every access to the shared data must take the same lock. A lock protects data, not code. If one thread updates counter without the lock, the whole scheme falls apart.
  2. Keep the critical section small. Anything inside the lock is single-threaded — you lose parallelism there. Put slow I/O, big computations, and printfs outside.
  3. Always unlock, even on error paths. If a thread grabs the lock and returns without unlocking, every other thread will wait forever. That's a deadlock.

The cost

Locking isn't free. The mutex demo runs measurably slower than the racy one — you traded raw speed for correctness. That's the fundamental tradeoff of concurrency: either the answers are right, or the runs are fast; you rarely get both for free.

This is why designers work hard to minimize shared mutable state — the less you share, the less you need to lock.

What can still go wrong

Deadlock

Thread A holds lock 1 and wants lock 2. Thread B holds lock 2 and wants lock 1. Both wait forever. Rule of thumb: always take multiple locks in the same global order.

Forgot-to-lock bug

One code path touches shared data without the lock. Everything works 99% of the time, then produces mysterious wrong answers. Every access must use the lock.

Held-too-long

Doing slow work while holding a lock (network I/O, heavy compute) serializes everyone. Get in, get out.

Check yourself

A mutex protects:

A mutex is a convention: "before touching this data, take this lock." If one thread skips the lock, protection fails. Always associate a mutex with a specific piece of data in your head.

A thread locks the mutex and then returns without unlocking. What happens?

Mutexes are not scope-bound in C. If you forget to unlock, the lock is held forever and other threads block forever. That's a classic deadlock.

Which is generally the best practice?

The critical section is single-threaded — you lose the point of having threads. Do the shared-data update, then release. Slow I/O and computation belong outside.

Try it yourself

  1. Compile and run the mutex demo. Verify you always get exactly 2 000 000.
  2. Time both versions with time ./race and time ./mutex_demo. Note the mutex version is noticeably slower — that's the correctness tax.
  3. Bonus deadlock: create two mutexes, a and b. Thread 1 locks a then b. Thread 2 locks b then a. Both should sleep 1 second between the two locks. Run it — it hangs forever. Kill it. That's your first deadlock, on purpose.
