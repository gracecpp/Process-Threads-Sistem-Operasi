Lesson 3 syscall + tiny C

wait() and zombies

A child finishes. Someone has to notice. Otherwise it lingers.

Recall

Last lesson, fork() gave us a parent and a child running side by side. Two questions we swept under the rug:

  • What happens when the child finishes first?
  • How does the parent find out?

The one idea

When a child process exits, the kernel does not immediately erase it. It keeps a tiny record — the child's PID and its exit status — so the parent can ask "how did my kid die?". That leftover record is called a zombie.

The parent claims the record by calling wait(). That call:

  1. Blocks (pauses) until a child exits, if none has yet.
  2. Returns the exited child's PID.
  3. Writes the child's exit status into an int you provide.
  4. Tells the kernel it's safe to erase the record. Zombie gone.
The bug this prevents

If a parent forks lots of children and never wait()s, every one becomes a permanent zombie. They take almost no memory each, but the PID table is finite. A long-running server that forgets to wait can eventually run out of PIDs.

See it in C

#include <stdio.h>
#include <stdlib.h>
#include <unistd.h>
#include <sys/wait.h>

int main(void) {
    pid_t rc = fork();
    if (rc == 0) {
        printf("child %d: doing work...\n", getpid());
        sleep(1);
        exit(42);            /* exit status = 42 */
    } else {
        int status;
        pid_t done = wait(&status);
        if (WIFEXITED(status)) {
            printf("parent: child %d exited with %d\n",
                   done, WEXITSTATUS(status));
        }
    }
    return 0;
}

$ ./wait_demo
child 52310: doing work...
parent: child 52310 exited with 42

The parent slept inside wait() until the child ran exit(42). Then the parent woke up, learned the PID and status, and cleaned up the zombie automatically.

Reading status

The int that wait() fills isn't a plain exit code — it's a packed value. Use the macros:

  • WIFEXITED(status) — true if the child exited normally.
  • WEXITSTATUS(status) — the actual exit code (only valid if the above is true).
  • WIFSIGNALED(status) — true if the child was killed by a signal (e.g. segfault).

The two undead states

Zombie

Child died, parent hasn't waited yet. Shown as Z or <defunct> in ps. Harmless one at a time; leaks in bulk.

Orphan

Parent died first, child still running. The kernel re-parents the child to PID 1 (init / systemd), which routinely calls wait(). So orphans are cleaned up automatically. Zombies aren't — because their parent is still alive and responsible.

Check yourself

A parent forks a child. The child exits. The parent never calls wait(). What is the child?

Child exited but its record can't be freed until the parent acknowledges it. That's the definition of a zombie.

A parent forks a child, then the parent exits immediately. The child keeps running. What is the child?

Children outlive their parents just fine. PID 1 becomes the new parent and will wait() for it when it finishes.

A parent calls wait(&status) before the child has exited. What happens?

wait() is blocking by design — it puts the parent to sleep until a child is reapable. Use waitpid(..., WNOHANG) if you want a non-blocking check.

Try it yourself

  1. Compile and run wait_demo.c.
  2. Make a zombie: in the child, call exit(0) after 1 second. In the parent, sleep(30) without calling wait(). While the parent sleeps, run ps -el | grep defunct in another terminal — you'll see the zombie.
  3. Fork three children in a loop, each sleeping a different amount, and wait() three times. Notice the parent gets them in the order they finish, not the order they were created.
