Lesson 4 syscall + tiny C

exec(): how the shell runs a program

fork makes a clone. exec turns the clone into someone else entirely.

Recall

fork() makes a copy of the current process. But if the copy runs the same program, how does the shell launch ls? It needs a way to say: "become a different program."

The one idea

The exec…() family of calls does exactly that. It says to the kernel: "Throw away my current program's code and memory, load this other executable in its place, and start running it from its main()."

The process's PID stays the same. Its open files stay the same. But its code, its data, its stack — all replaced. From the outside, it's the same process; from the inside, it woke up as a completely new program.

The Unix pattern

Almost every program on your system was started this way: fork, then exec. Fork gives you a fresh process to sacrifice. Exec turns it into the program you actually wanted to run. This is how your shell runs ls, how make runs gcc, how a web server spawns a CGI script.

See it in C

#include <stdio.h>
#include <unistd.h>
#include <sys/wait.h>

int main(void) {
    pid_t rc = fork();
    if (rc == 0) {
        /* child: become "ls -l /" */
        char *argv[] = {"ls", "-l", "/", NULL};
        execvp("ls", argv);
        perror("execvp failed");   /* only reached if exec failed */
    } else {
        wait(NULL);
        printf("parent: ls is done\n");
    }
    return 0;
}

$ ./shell_lite
total 68
drwxr-xr-x   2 root root  4096 ... bin
...
parent: ls is done

Read that program carefully. The child called execvp and never came back. The line after it (perror) only runs if exec failed — because on success there is no "after"; the whole program has been replaced by ls.

Why the family of names?

All the exec… calls do the same thing; they differ in argument style:

  • execv — takes an array of arguments.
  • execl — takes a list of arguments (as varargs).
  • …p suffix (execvp, execlp) — searches your $PATH, so you can say "ls" not "/bin/ls".
  • …e suffix — lets you pass a custom environment.

Mnemonic: vector, list, path, environment. Mix and match.

The full shell recipe

Every interactive shell (bash, zsh, sh) is basically this loop:

while (read_command(&cmd)) {
    pid_t rc = fork();
    if (rc == 0) {
        execvp(cmd.name, cmd.argv);   /* becomes the requested program */
        exit(1);                       /* only if exec failed */
    } else {
        waitpid(rc, NULL, 0);          /* wait for it to finish */
    }
}

That's it. Everything else — pipes, redirection, background jobs, job control — is decoration on this core.

Why the split?

It would seem simpler if there were one call spawn(program, args). Unix chose to split it into fork + exec because of what you can do between them: while you're in the freshly-forked child but before you exec, you can close/redirect file descriptors, change directory, drop privileges, set up a new environment. That's how the shell implements >, <, and | — plain old syscalls between fork and exec.

Check yourself

After a successful exec(), does the code line right after it run?

On success, the old program is entirely replaced — there is no "next line". Code after exec only runs if the call failed.

You exec() a new program. What is its PID?

exec keeps the same PID — same process, new program. Only fork makes new PIDs.

Why does the shell fork before exec, instead of just exec-ing?

If the shell exec'd directly, its own program would be replaced by ls and disappear. Fork gives us a sacrificial child to exec, so the shell survives to prompt again.

Try it yourself

  1. Run shell_lite.c as written. Then change "ls" to "/bin/date" and drop the args (just {"date", NULL}).
  2. Delete the fork() and just call execvp directly. Compile and run. Notice: your program becomes ls and never prints "parent" — that's the point of forking first.
  3. Bonus: between fork and exec in the child, add freopen("out.txt", "w", stdout);. Now ls's output lands in out.txt. Congratulations — you just implemented >.
